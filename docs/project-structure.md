Complete overview of the project organization, file purposes, and architectural decisions.

│   ├── typescript-setup.md  # TypeScript configuration

├── .claude/                 # Claude Code configuration

## Directory Purposes

### `src/` - Source Code

**Purpose**: Contains all TypeScript application source files.

**Current contents**:
- `index.ts`: Main entry point with basic "Hello World" functionality

**Future organization**:
As the application grows, this directory might include:
```
src/
├── services/              # Business logic services
├── utils/                 # Utility functions
├── types/                 # TypeScript type definitions
├── config/                # Configuration files
└── index.ts              # Entry point
```

**Key principles**:
- Keep files focused and single-purpose
- Use TypeScript interfaces for data structures
- Export public APIs, keep implementation details private
- Organize by feature, not by layer

### `dist/` - Compiled Output

**Purpose**: Contains compiled JavaScript files from TypeScript compilation.

**Generated contents** (not in source control):
- `index.js`: Compiled JavaScript
- `index.js.map`: Source map for debugging
- `index.d.ts`: Type declarations
- `index.d.ts.map`: Type declaration source map

**Management**:
- Generated by `npm run build`
- Should not be manually edited
- Excluded from git via `.gitignore`
- Used by `npm start` for production execution

### `tests/` - Test Files

**Purpose**: Contains all test specifications for the application.

**Current contents**:
- `example.test.ts`: Basic setup verification tests

**Future organization**:
```
tests/
├── unit/                  # Unit tests
├── integration/           # Integration tests
├── services/              # Service tests
└── utils/                 # Utility tests
```

**Naming convention**:
- Test files must end with `.test.ts`
- Mirror `src/` structure when applicable
- Use descriptive test names

**Key principles**:
- Test behavior, not implementation
- Keep tests independent
- One assertion per test when possible
- Use descriptive test names

### `docs/` - Technical Documentation

**Purpose**: Comprehensive technical documentation for the project.

**Current contents**:
- `commands.md`: NPM command reference
- `typescript-setup.md`: TypeScript configuration details
- `testing-guide.md`: Testing with Vitest
- `code-quality.md`: ESLint and Prettier guide
- `project-structure.md`: This file

**Future additions**:
- API documentation
- Architecture diagrams
- Deployment guides
- Contributing guidelines

**Maintenance**:
- Keep documentation updated with code changes
- Use clear, concise language
- Include examples for complex concepts
- Maintain consistent formatting

### `node_modules/` - Dependencies

**Purpose**: Installed npm packages and dependencies.

**Management**:
- Generated by `npm install`
- Should never be manually edited
- Excluded from git via `.gitignore`
- Recreated on different machines via `npm install`

**Key dependencies** (devDependencies):
- **TypeScript**: typescript, @types/node, ts-node
- **Testing**: vitest, @vitest/coverage-v8
- **Code Quality**: eslint, typescript-eslint, prettier

## Configuration Files

### `package.json` - Project Metadata

**Purpose**: Defines project metadata, dependencies, and scripts.

**Key sections**:
- **Metadata**: name, version, description, author, license
- **Scripts**: All npm commands (dev, build, test, etc.)
- **Dependencies**: Runtime packages (currently none)
- **DevDependencies**: Development tools

**Important fields**:
```json
{
  "type": "module",              // ES modules
  "main": "dist/index.js",      // Entry point
  "scripts": { ... },            // Commands
  "keywords": [ ... ],          // Discovery
  "devDependencies": { ... }   // Build tools
}
```

### `tsconfig.json` - TypeScript Configuration

**Purpose**: Defines TypeScript compiler options and file inclusion.

**Key settings**:
- **Strict mode**: Maximum type safety
- **Target**: ES2022 (modern JavaScript)
- **Module**: NodeNext (latest Node.js modules)
- **Output**: dist/ directory

**See**: `docs/typescript-setup.md` for complete details.

### `eslint.config.js` - Code Quality Configuration

**Purpose**: Defines ESLint rules for code quality and consistency.

**Structure**:
- Base JavaScript rules
- TypeScript-specific rules
- Type-aware checking rules
- Custom project rules
- Prettier integration

**See**: `docs/code-quality.md` for complete details.

### `.prettierrc` - Code Formatting Configuration

**Purpose**: Defines Prettier formatting rules.

**Key settings**:
- Single quotes
- 2-space indentation
- Trailing commas
- Semicolons required
- 100 character line width

**See**: `docs/code-quality.md` for complete details.

### `.gitignore` - Git Exclusions

**Purpose**: Defines files that Git should ignore.

**Excluded patterns**:
- `node_modules/` - Dependencies
- `dist/` - Build output
- `.env*` - Environment files
- `*.log` - Log files
- IDE files (`.vscode/`, `.idea/`)
- OS files (`.DS_Store`, `Thumbs.db`)

### `CLAUDE.md` - Project Instructions

**Purpose**: Provides context and instructions for Claude Code AI assistant.

**Contents**:
- Project goals and principles
- Technology choices
- Development workflow
- Learning objectives
- Collaboration guidelines

**Usage**: Read by Claude Code to understand project context and requirements.

## File Naming Conventions

### TypeScript Files
- **Source files**: `.ts` extension
- **Test files**: `.test.ts` extension
- **Declaration files**: `.d.ts` extension (generated)
- **Use lowercase with hyphens** for multi-word files: `user-service.ts`

### Directories
- **Use lowercase with hyphens**: `user-service/`
- **Avoid spaces and special characters**
- **Keep names descriptive but concise**

### Configuration Files
- **Use standard names**: `.eslintrc.js`, `.prettierrc`, etc.
- **Prefix with dot for hidden files** (Unix convention)

## Import/Export Patterns

### Module System
- **ES Modules**: Uses `import`/`export` syntax
- **File extensions**: Not required in imports (TypeScript resolves)
- **Index files**: Can use `/index` or just `/`

### Examples

```typescript
// Import from same directory
import { helperFunction } from './helpers';

// Import from subdirectory
import { UserService } from './services/user-service';

// Import types
import type { User, UserData } from './types';

// Export individual items
export function processData(input: string): string { ... }
export const API_URL = 'https://api.example.com';

// Export as module
export default class DocumentProcessor { ... }
```

## Development Workflow by Directory

### Working in `src/`
1. Create or modify TypeScript files
2. Run `npm run dev` to test immediately
3. Run `npm run typecheck` to validate types
4. Run `npm run lint` to check code quality
5. Run `npm run format` to fix formatting

### Working in `tests/`
1. Create test file with `.test.ts` extension
2. Import functions from `src/` to test
3. Write descriptive test cases
4. Run `npm test` to execute tests
5. Run `npm run test:coverage` for coverage report

### Updating Configuration
1. Modify config file (tsconfig.json, etc.)
2. Test changes with relevant commands
3. Commit changes with descriptive message
4. Update documentation if behavior changes

## Architectural Principles

### Current Architecture

**Minimal Foundation**:
- Single entry point (`src/index.ts`)
- Basic verification tests
- No external dependencies (AWS, frameworks)
- Clean, simple structure

**Why this approach**:
- **Learning**: Focus on Node.js/TypeScript fundamentals first
- **Simplicity**: Avoid premature architecture
- **Evolution**: Let structure emerge from requirements
- **Testing**: Easy to test and verify setup

### Future Architecture (When Needed)

As requirements emerge, the structure may evolve to include:

**Service Layer** (for AWS integration):
```
src/services/
├── textract-service.ts
├── bedrock-service.ts
└── s3-service.ts
```

**Configuration Layer**:
```
src/config/

**Type Definitions**:
```

├── document-types.ts

**Utilities**:

### Guiding Principles

1. **Start Simple**: Begin with minimal structure
2. **Add Structure Purposefully**: Only when beneficial
3. **Follow TypeScript Conventions**: Use modern patterns
4. **Keep Files Small**: Single responsibility per file
5. **Explicit Over Implicit**: Clear naming and exports
6. **Testable Design**: Structure supports easy testing

## File Organization Best Practices

### 1. Cohesion
- Group related functionality together
- Keep related files in same directory
- Use clear directory names

### 2. Coupling
- Minimize dependencies between modules
- Use interfaces to define contracts
- Avoid circular dependencies

### 3. Naming
- Use descriptive, meaningful names
- Follow TypeScript conventions
- Be consistent across project

### 4. Imports
- Import only what's needed
- Use type imports for types: `import type { ... }`
- Organize imports logically

### 5. Exports
- Export public APIs explicitly
- Keep implementation details internal
- Use default exports for main exports

## Git Strategy

### Files to Commit
- All source code (`src/`, `tests/`)
- Configuration files (`package.json`, `tsconfig.json`, etc.)
- Documentation (`docs/`, `CLAUDE.md`, `README.md`)
- Project files (`.gitignore`, `.prettierrc`)

### Files to Exclude
- `node_modules/` (dependencies)
- `dist/` (compiled output)
- `*.log` (log files)
- `.env*` (environment secrets)
- IDE files (`.vscode/`, `.idea/`)

### Commit Patterns
- **Feature**: "Add user authentication system"
- **Fix**: "Fix null reference in document processing"
- **Refactor**: "Refactor service layer for better separation"
- **Docs**: "Update testing guide with new examples"
- **Config**: "Update TypeScript to version 5.9"

## Continuous Improvement

### Review Points
- **Weekly**: Review file organization
- **Per Feature**: Evaluate structure changes
- **Per Release**: Update documentation
- **Continuous**: Refactor for clarity

### Evolution Signals
- Files becoming too large → Split functionality
- Complex imports → Reorganize structure
- Repeated patterns → Extract to utilities
- Hard to test → Restructure for testability

### Documentation Maintenance
- Update docs when structure changes
- Add examples for new patterns
- Keep guides current with tools
- Document architectural decisions
